# Mirage security model

Honest scope: this describes what the code does today and what it does not. No external audit, no SOC 2.

## Threat model
| Threat | Mitigation in code | Residual risk |
|---|---|---|
| **Deepfake of a person who did not consent** (core abuse case) | A replica cannot become `ready` without a consent record (`safety.require_consent`). Consent = the person records their voice reading a random phrase with 3 random code words (single use, 15 min). Server transcribes (faster-whisper), fuzzy-matches the phrase (score >= 0.8, all code words in order, tolerant to ASR slips but never to a different code word), stores the audio + sha256, and compares the voice to the one in the training video (WeSpeaker ResNet34 embedding, cosine >= 0.50). | See "Consent limits" below. |
| Voice/face used to say harmful things | Blocklist + optional LLM classifier on scripts, checked at the API and again in the worker. | Classifier is imperfect (9/9 on a small sample set; not a benchmark). Real-time conversation output is not moderated frame by frame. |
| Guessing/scraping file URLs | `/v1/files/*` need an HMAC-signed `exp`+`sig` link (default TTL 1 h, `POST /v1/files/sign` after an owner check; `output_url` fields in API responses and webhook payloads are signed automatically). Unsigned access exists only in dev or with `MIRAGE_ALLOW_PUBLIC_FILES=1`. A wrong signature never falls back to public access. | Anyone who holds a link can use it until it expires. Revoke everything by rotating `MIRAGE_SECRET_KEY`. |
| API abuse / cost exhaustion | Rate-limit middleware (per IP for everything, per API key, tighter per-route: signup, video creation, checkout, conversations, replica create, moderation), 429 with `Retry-After`; request size caps (413); credit checks. | In-process counters: per worker, reset on restart (use a shared store before running several workers). WebSockets: connection-rate limits per IP and per account, failed-auth budget per IP, per-connection message/byte budgets and frame-size caps, and a per-account cap on concurrent live conversations (default 5; guest/widget sessions are exempt from that cap because they are the host's visitors, not the host's own sessions). Signup: see "Bot-resistant signup". A botnet with many IPs and real mailboxes can still sign up repeatedly (no email verification). |
| Browser attacks on the API | Security headers (nosniff, DENY framing except the embeddable playground, no-referrer, CSP `default-src 'none'` on JSON, HSTS in production, `no-store` on JSON). CORS is an explicit allow-list (production refuses `*`). | The dashboard stores the API key in `localStorage`: any XSS steals it (see "Dashboard key storage"). The legacy signup key is stored in plaintext in the DB (multi-keys are hashed). The WebSocket no longer takes the key in the URL by default (tickets, below). |
| SSRF via training-video / photo / listening-clip / webhook / tool / custom-LLM URLs | `netguard.py`: one guarded httpx transport for every user-supplied URL; refuses non-public addresses after DNS resolution (loopback, RFC1918, metadata 169.254.169.254, CGNAT, ULA, mapped forms), pins the connection to the validated IP (no DNS rebinding), re-checks every redirect hop, http(s) only, 300 MB cap. Default ON in production (`MIRAGE_BLOCK_PRIVATE_URLS`). | Operator-configured internal services (Ollama, lip-sync) are intentionally unguarded; worker scripts that fetch model weights from fixed URLs are not guarded. |
| Secrets in logs | Every log record (any logger, uvicorn access log, exceptions) is scrubbed at creation of API keys, `api_key=`/`token=`/`sig=` values and Bearer tokens; created keys are shown once; tests assert keys never appear in responses, `/metrics`, audit or logs. | The single-use `?ticket=` is also scrubbed; it is useless after one connection or ~30 s. With `MIRAGE_ALLOW_KEY_IN_URL=1` the key is again exposed to proxy/CDN logs. |
| **Impersonation: consent from someone other than the face shown** | Selfie video recorded while reading the phrase; SFace face embedding compared with the photo / training video (median of best cosine >= 0.45, measured, conservative); same clip feeds ASR and voice match so face and voice are tied to one recording; video is discarded, only scores + hash kept. | Look-alikes/relatives; thresholds measured on few identities. |
| **Consent bypass: photo / printed picture / phone held to the camera** | Passive liveness (face present, non-rigid landmark motion, mouth motion, registered mouth-region change); simulated held, tilted and shaken photos rejected in tests. | Heuristic, not certified. A replayed video of the real person, or a virtual camera deepfake, passes. |
| **Consent bypass: typed consent, audio-only, replayed phrase** | Typed path disabled in production; production needs voice + face + live check; random single-use phrase with 3 code words, 15 min; worker gate re-verifies a matching face binding. | Live TTS-cloned voice + injected video. |
| Over-privileged keys | `scope=read` API keys (GET only). | WebSocket paths not scope-checked (minting a ticket is a POST, so read-only keys cannot). |

## WebSocket tickets, limits and session caps
- **No key in the URL.** `POST /v1/realtime/ticket {conversation_id}` (key in the `x-api-key` header) returns a ticket that is single use, bound to that account and conversation, and expires in `MIRAGE_WS_TICKET_TTL` (30 s). The bundled client (`mirage-client.js`, `playground.html`) fetches a new ticket on every (re)connect. `?api_key=` is refused unless `MIRAGE_ALLOW_KEY_IN_URL=1` (default off everywhere, dev included). Tickets live in process memory: with several workers a ticket must be redeemed by the worker that minted it (sticky routing) or move the store to a shared one. Guest/widget sockets authenticate with the share token as before (no key involved).
- **Limits** (env, `limit/window`): `MIRAGE_WS_CONNECT_IP` 120/60, `MIRAGE_WS_CONNECT_ACCOUNT` 60/60, `MIRAGE_WS_AUTH_FAIL_IP` 15/60 (brute force of tickets/keys), `MIRAGE_WS_MAX_SESSIONS` 5 live conversations per account (reconnects to the same conversation do not count), per connection `MIRAGE_WS_MSG_RATE` 200/s (burst 400) binary and `MIRAGE_WS_TEXT_RATE` 40/s (burst 80) text frames, `MIRAGE_WS_BYTES_RATE` 2 MB/s, frames above 64 KB (binary) / 1 MB (text) close with 1009; violations close with 4429. The numbers are defaults chosen against the bundled client (50 audio frames/s); they are not tuned on real traffic.
- **Limits of the limits:** per process, reset on restart; a client that stays under the budget can still hold a session open until credits or `max_seconds` run out; the admission controller (capacity) is the global brake.

## Bot-resistant signup (no external service)
Layers in `signup_guard.py`: email syntax check; blocklist of ~150 disposable domains (+ subdomains, extend with `MIRAGE_BLOCKED_EMAIL_DOMAINS`, disable with `MIRAGE_BLOCK_DISPOSABLE_EMAIL=0`); honeypot field `website` (bots that fill it get a fake success with a useless key and no account); per-IP burst limit (existing), per-IP daily cap (`MIRAGE_SIGNUP_PER_IP_DAY`, 10 in production) and a global hourly cap (`MIRAGE_SIGNUP_GLOBAL_HOUR`, 300 in production); one account per normalised address (gmail dots and `+tag` folded; production default, `MIRAGE_SIGNUP_UNIQUE_EMAIL`); optional proof of work (`MIRAGE_SIGNUP_POW_BITS`, off by default; 18-20 is roughly 0.3-3 s in a browser; HMAC-signed stateless challenge, 5 min, single use per process). The web signup page ships the honeypot and the solver.
**Not stopped:** attackers with many IPs and real or catch-all mailboxes (no email verification, no CAPTCHA), disposable domains not on the list, headless browsers that solve PoW (it only prices them). The global hourly cap can be used to lock real users out of signup (a cheap DoS), which is why it is generous. Turn PoW on if you see abuse; add email verification before launch if signups carry real cost (they grant 600 free seconds).

## Dashboard key storage (localStorage): assessed
Verdict: **not removable without a backend rewrite, partly mitigated, residual risk accepted and stated.** The API authenticates only with the `x-api-key` header (no cookie sessions), and a static Next dashboard on another origin has to hold the key somewhere script can read: `localStorage`, `sessionStorage` or memory. Moving to `sessionStorage` would only trade persistence for login friction (new tab = signed out) and does not stop XSS. An httpOnly cookie session needs a new backend auth path with CSRF protection: that is the real fix, and it is not done.
What changed: (1) the key is no longer put in iframe URLs (it used to go in `playground.html?api_key=...`, into history and server logs); the dashboard now hands it to the framed playground with `postMessage` addressed to the API origin only; (2) the playground strips a legacy `?api_key=` from the address bar; (3) the dashboard sends a CSP (`next.config.js`) whose `connect-src` is this origin + the API, `object-src 'none'`, `frame-ancestors 'none'`, so injected script cannot exfiltrate the key with fetch/XHR/WebSocket to a third-party host; (4) tickets mean a key never appears in a WebSocket URL. Still true: the CSP keeps `script-src 'unsafe-inline'` (Next hydration), so it limits exfiltration rather than preventing XSS; image/navigation-based exfiltration to the API origin and DOM-reading are not covered; any XSS in the dashboard can still use the key while the page is open. Mitigations for users: create a `scope=read` key for read-only dashboards, rotate keys (`POST /v1/keys/legacy/rotate`), keep third-party scripts off the dashboard origin.

## Static page headers (CSP)
Checked on a live server and in Chromium. Findings fixed: `/static/playground.html` was sent with `X-Frame-Options: DENY`, so the dashboard iframe was blocked by real browsers (the e2e script opened it top-level and never noticed); `/v1/playground` had no framing restriction (clickjacking a microphone page); no HTML page had a CSP; `mirage-client.js` used `new Function` (needs `unsafe-eval`), now a plain function. Now: HTML pages (`/static/*.html`, `/v1/playground`, `/guest/*`, `/widget/frame/*`) get `default-src 'self'`, no objects/base/forms, `connect-src` limited to the page host (+ ws/wss), `img-src` self/data/blob; the playground may be framed only by `'self'` and the explicit `MIRAGE_CORS_ORIGINS` (never `*`); guest pages deny framing; widget frames keep their per-widget `frame-ancestors` and add the page policy. `nosniff`, `no-referrer`, `COOP same-origin` everywhere; HSTS in production. Residual: the pages contain inline `<script>` so `script-src` has `'unsafe-inline'` (moving them to files or hashes is future work); `playground.html` accepts a key from the URL for old links and from a parent frame by `postMessage` (only from `window.parent`).

## Consent limits (read before relying on it)
1. **Not liveness detection.** Someone who owns a recording of the real person's voice (or a good voice clone of them) and can play it into the microphone can pass: the check proves the *audio* says the random phrase in a voice that matches the video, not that the human is present. The random phrase makes pre-recorded replay hard, not live TTS-cloning attacks.
2. **Face binding (new).** The consent recording is a selfie video; the face in it is matched to the replica's photo or training video (SFace, threshold 0.45) and checked with passive liveness heuristics. Not certified liveness; see docs/overnight/consent-security.md for what it does and does not stop (screen replay and injected deepfake video pass; person B's voice over person A's face is not checked for lip-sync).
3. The voice model is a general speaker verifier. Our test: same speaker scored 0.82-0.91, different (synthetic) speakers 0.01-0.41, one human-vs-TTS pair 0.04-0.14. Real-world noise, codecs, illness and short clips shift scores; the 0.50 threshold is untuned on real consent data. Expect false rejects on bad audio and some false accepts on close relatives/impersonators.
4. English ASR only (`base.en`). A mispronounced name may lower the phrase score but code words decide.
5. The reference voice comes from the first 60 s of the training video: if that video has several speakers or music, scores are unreliable (production enforces, so it would reject; dev only warns).
6. The typed-phrase path (`POST /consent`) is a dev convenience and is disabled in production (`403 typed_consent_disabled`).
7. Stored consent audio is private (owner-only endpoint) and kept until the replica is deleted. Revoking consent marks records revoked; `DELETE /v1/replicas/{id}` removes everything.

## Data retention and deletion
- `DELETE /v1/replicas/{id}`: deletes the replica row, its videos (rows + MP4s), the replica folder (source video copy, face, voice reference), consent recordings and verification rows, consent challenges, job rows, and every other table that references the replica or its videos (discovered from the schema, so future tables are covered). Personas survive with `replica_id = null`.
- `POST /v1/account/delete-my-data` `{"confirm":"delete-my-data"}`: deletes everything owned by the account (replicas, videos, personas, knowledge, conversations, API keys, ...) and the account row, then the key stops working.
- Covered and tested for every table and data directory (schema-driven test): consent audio, face reference templates, voice clones, listening clips, photo avatars, rendered videos + thumbnails/captions, creative assets, stored perception frames, owned workspaces, API keys and scopes.
- **Kept on purpose:** ledger entries and payment events (financial records), the audit log, and a `datadeletion` tombstone (ids and counts only). Document your own retention policy; a legal retention period may apply.
- Not covered: database backups and copies you made; LLM provider logs if you configure a hosted LLM; Ollama keeps no data. Webhook receivers keep what they received.

## Operator checklist
0. Leave `MIRAGE_ALLOW_KEY_IN_URL` unset. Set `MIRAGE_SIGNUP_POW_BITS` (e.g. 18) if signup abuse appears; consider email verification. Run one API worker (or add shared state) until tickets/limits move out of process.
1. `MIRAGE_ENV=production`, strong `MIRAGE_SECRET_KEY`, explicit `MIRAGE_CORS_ORIGINS`.
2. TLS in front; `MIRAGE_TRUST_PROXY=1` only if behind your proxy.
3. Keep port 8100 (lipsync), 11434 (Ollama), and the DB private.
4. Download the speaker model (`make models`); production returns 503 `voice_unavailable` for consent without it (fail closed).
5. Tune `MIRAGE_VOICE_MATCH_THRESHOLD` on your own consenting users before launch.
6. Back up DB + data together; test a restore.
